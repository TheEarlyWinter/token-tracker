## 已确认问题

### 看板

- 旧慢请求可以覆盖新的筛选结果。
- 离开页签后改筛选，返回仍显示旧数据。
- 筛选不变时，后台新增记录不能触发路由视图更新。
- 已成功加载后的刷新错误被隐藏。
- provider 筛选未贯通。
- 分页和刷新可能竞争，强制扫描可能被普通在途查询吞掉。
- 只取前十项的排行榜被描述成完整模式数。
- 原文案把模型标识不同直接描述为实际模型偷换，证据不足。

### 采集与存储

- 缺少 responseId 的同一消息会生成随机 ID，重复扫描可重复计数。
- SQLite 重复写入也返回新增成功，导致 newRoutes 虚高。
- 日期按 UTC 存储，查询却按应用时区计算。
- 月初等区间计算混用了进程时区。
- 首次 dataDir 不存在时会静默退回内存，重启丢失记录。
- 迁移失败后仍可能对不完整表查询。
- 供应商与复合模型筛选缺失。分页参数缺少一致规则。
- API 会回显内部数据库错误。
- 扫描进度过早缓存，写入失败后不易重试。

## 修复原则

- 新消息与历史扫描使用同一确定身份。
- 保留原 responseId_timestamp 形式，兼容已部署记录。
- 只复用有真实旧随机 ID 格式且身份能精确匹配的记录。
- 不合并两个不同的合法响应 ID。
- 保留旧行，不自动清库或合并无法确认的重复记录。
- schema 迁移采用事务，只补已知旧版本缺列。
- 初始化失败时明确返回存储不可用，不伪装空历史。
- 查询入口只校验一次。状态切片只筛列表，不改变 KPI 分母。
- 普通查询不扫描磁盘。明确的全面扫描才触发历史读取。
- header 有界读取并缓存。增量扫描只读追加字节。
- Token 同时支持当前扁平消息和项目已有结构化口径。

## 复审记录

第一轮实施后，主代理又复现了三个问题：

1. 旧行匹配过宽，把不同 responseId 的合法调用误合并。
2. 旧文件名会话 ID 与新 header ID 不同，导致重复入库。
3. 先整文件读取再切片，不是真正的增量读取；每条消息还重复读取 header。

对应修复均补充了合成回归和实际读取字节检查。
独立复查还确认子代理历史目录遗漏。最后一轮已补普通 sessions 和 subagent-sessions 的递归发现。不跟随 symlink，不扫描其他目录。子代理历史按所属目录归类，不新增实际执行者推断。

完整的无 LF 尾行立即录入。不完整尾行等待补齐。扫描失败时不发布新游标。
强扫先完成参数校验，再读取可信历史路径。HTTP refresh=true 保留原强扫别名；UI 内部 refresh 选项只表示重新查询，两者不混用。
afterScan 等待 Agent 名称刷新。失败只记录安全错误码。
主代理又核对结构化 Token 口径：input.totalTokens=100、output=20 时，总量为 120，不能再加 cacheWrite。

### Codex 返回标识的采集限制

后续只读调查确认：当前宿主的 Codex Responses 适配器没有把上游 response.model 写入消息 responseModel。离线合成响应可以复现这个缺口。
因此，即使记录显示目标模型与返回模型同名，也不能证明这类调用未被路由。历史记录本身不能补出未保存的返回标识。
部分 OpenAI Completions 兼容接口会保存不同的返回模型名，不能把两条协议的采集能力视为相同。
本版未修改宿主或其依赖，也未解决这个采集缺口。
