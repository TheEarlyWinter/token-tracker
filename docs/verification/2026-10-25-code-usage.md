## 历史与性能边界

已删除、拒权或缺namespace的会话不能猜测分类。仍计入原类别与总量，并提示Code分类可能不完整。历史会分批识别，不承诺安装后立即全部回填。

每扫描最多8次官方会话查询，全局最多2个在途，单次等待2秒，失败至少冷却5分钟。候选与待提交映射均有256上限。SQLite永久写失败时，主统计继续、明细回退聚合，但每轮全量重建可能增加CPU和磁盘开销；本轮不加入通用重试框架。来源流图和趋势图的Code颜色可能不同，仅为视觉差异。

## 方案取舍与代价

1. Code沿用互斥type，不增加独立namespace筛选。以后若需来源和执行角色交叉筛选，须另扩展。
2. 串行实施并保留开发分支、源码和记录，不批量清理。多占少量磁盘，不推送、不合并、不发布。
3. 以数据代次核对SQLite，按真正落盘映射确认，并等快照成功后ack。增加少量元数据写入；故障注入测试覆盖旧明细及丢分类风险。
4. 聚合提交使用持久pending屏障。异常重启时保守重建，增加少量写盘和恢复开销。
5. 原始归档纯追加沿用数量覆盖核对，不另加聚合屏障。前提是唯一请求只追加、不原地改写；未来若允许同数量修改，必须升级恢复校验。
